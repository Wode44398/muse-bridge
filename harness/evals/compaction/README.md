# 压缩召回 eval（Q6 / N47）

压缩是有损的。改压缩（R10）之前先要有尺子：压完之后，要被压掉的那段里的事实还剩多少？反复压几轮之后呢？

## 怎么量

1. **语料 = 真实会话的副本。** 会话文件先整份复制进临时目录再读，跑完删掉。现实里已经压缩过的会话跳过——原来的中段
   已经不在记录里了；按所选窗口压不起来的短会话也跳过。
2. **回放走生产代码。** 把会话按原顺序一条条放进生产的 `AgentState`，每次「要请求模型之前」（用户消息 / 工具结果之后）
   调生产的 `ensureContextFits`：微压缩、切分、摘要、熔断都是生产代码，这里一行不抄（`replay.ts`）。窗口默认模拟
   32K（比真实的小），好让中等长度的会话也压上好几轮。
3. **考题是机械抽的锚点**（`anchors.ts`）：改过的文件、失败工具报的错误码 / 错误类型、提交哈希 / URL / UUID、用户原话。
   只数「来源已不在上下文里原样出现」、而且原样保留的部分里也找不到的锚点。
4. **判分是字符串匹配**，两种：
   - **在场**：压完之后，锚点还能不能在上下文（摘要等）里找到。每次整段压缩后都量，按「被压过几轮」分桶——
     0 轮 = 刚压进摘要，1 轮 = 它所在的摘要又被压了一次……单调掉到底 = 老信息在反复压缩里蒸发。
   - **答题**（`answer.ts`）：让模型只看回放结束时的上下文答题（每种锚点问一次），答案里找不找得到。
5. **反复压缩模拟**：每次整段压缩腾出多少、压完剩多少（相对触发线）。腾出比例连续单调下降、最后不到 20% 记为棘轮
   嫌疑（hermes 评估外部方案时就是这样发现它会卡死的）。

臂：`current` = 生产压缩；`drop` = 同样切分、LLM 笔记为空。R10 起摘要消息里除了 LLM 笔记，还有原样保留的用户原话与机械
锚点索引（都不经摘要器），所以 drop 不再是零——它量的是 LLM 笔记本身在这之上多贡献了多少。`recovery`（R10 二）= 生产压缩
再接上压缩归档（内存里；生产的 compact() 照常写、摘要末尾照常列出）。答题时先闭卷答一次（与 current 同一个问法），再给
Grep / Read 让模型翻归档、只回闭卷答案里缺的，计分取两次的并集——量的是 Context Recovery 在上下文之外额外找回多少；收据里
闭卷与加回查分开列，另记回查调用次数。在场召回与 current 同口径（只看上下文）。（第一版协议一上来就给工具，模型只报 grep
到的那几十行、丢了上下文里现成的，答题召回反而更低——见 results/2026-09-24-r10b-recovery-prod.md。）

## 怎么跑

```bash
node evals/compaction/run.ts --sessions <会话目录> --topic baseline
```

- `--model` 默认 `local/qwen3.8-27b`（本机 llama-server 要先起好）；云端模型的 key 从环境变量读。
- `--window 32768`、`--arms current,drop`（可加 `recovery`）、`--no-answer`（只量在场，不答题，快得多）、`--limit 20`（最长的 20 个会话）。
- 改压缩时：在改前 / 改后两棵工作树里、对同一份语料各跑一次，对照两张收据。

收据写进 `results/<日期>-<主题>.md`：**只有数字和会话 id 前 8 位**。锚点本身（路径、哈希、用户原话）是会话内容，
不进仓库——`server/compaction-eval.test.ts` 查的就是这个。

## 自检

`server/compaction-eval.test.ts` 用合成的长会话和脚本化的摘要器证明这把尺子量得对：回放调的是生产的摘要请求；
用户原话与锚点索引一路带下去，「会忘掉旧事实」的摘要器在 1 轮以上的桶里也大半找得回；drop 臂只拿掉 LLM 笔记；答题臂每种锚点
只问一次；回查臂的答题者 Grep 得到归档里的原文，Grep / Read 的输出贴着生产的格式；收据里没有会话内容。
