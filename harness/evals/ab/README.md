# 本机 A/B 评测台（Q6 / N46）

改动会不会让模型「变笨」——单测答不了，要让真模型在陷阱任务上跑，两边比。这里就是那张台子。

## 怎么跑

两棵工作树 = 同一个仓库的两个 git worktree（改动前 / 改动后）。在任意一棵的 `harness/` 下：

```bash
node evals/ab/run.ts --base ../claude-bridge-base --head . --topic q7-hints --reps 3
```

- `--model` 默认 `local/qwen3.8-27b`（本机 llama-server，要先在「本机」胶囊里起好；两臂轮流跑、不并行，单 GPU 够用）。
  用云端模型时加 `--env-file <.env>` 给这一臂读 key。
- `--tasks id1,id2` 只跑部分任务；`--ports` 默认 `8851,8852`。
- 一批 6 任务 × 2 臂 × 3 次大约一两个小时，适合夜里后台跑。中断了原样重跑，已完成的会跳过（账本 `%TEMP%/dimensio-ab-<日期>-<主题>/meta.jsonl`）。
- harness 起不来、接口报错这类基础设施失败不入账，只打一行 `!`。

每臂是一个独立的 harness 进程，所有落盘目录（会话、记忆、知识、配置、项目、工作区）都在这一臂的临时根里，不碰任何真数据；
令牌由 runner 生成注入。改道靠的是 Q8 的数据路径收口（`server/paths.ts`）：**两臂都必须是 Q8 之后的代码**，更早的代码
有落盘位置不认环境变量（设工作区就会写 runtime-config），runner 直接拒绝。所以在 main 合进 Q8 之前，不能拿正式服的代码当 base。

## 结果怎么读

结果写成 `evals/ab/results/<日期>-<主题>.md`，这就是**决策收据**：在对应改动的提交说明里引用它。

- n=3 只看方向，不是统计显著。
- 低于 100% 的格子必须逐 run 审——报表里附了每次没通过的判分细节、收场方式与末尾输出。
- 轮数 / 工具调用 / 失败调用 / 门禁追问的均值来自会话记录（`server/session-health.ts` 的统计），和体检脚本同一套口径。

## 任务

`tasks.ts`，都取自 dimensio 自己的事故档案，每个写明出处（`origin`）。判分只看磁盘状态与会话记录，是确定性的；
「真的好了没有」一律自己跑测试判，不信模型自己说的。

前 6 个是编码陷阱；瘦身 P0（2026-10-07）补了 6 个日常形态：纯问答、看一眼工作区就答、文档整理、用户表达长期偏好（判分
看这一臂的记忆根里记没记下来——`check` 的第三个参数 `env.memoryDir`）、做网页并用浏览器验证、多步实现。

成本一栏按会话用量账本的全部任务合计（主循环 + 子 agent + 压缩摘要 + 记忆沉淀）；收尾后的记忆沉淀在后台跑，runner 等
状态接口的 `memoryPending` 消失再判分。

加任务：写 `setup`（在空目录里摆现场）、`check`（判分）、`reference`（参考解）。`server/ab-eval.test.ts` 会检查每个
任务原样现场判不通过、做完参考解判通过——陷阱没有预先解开，判分也不是永远过不了。同一个文件还用假 provider 把整条
管线跑一遍（起进程、发任务、读记录、判分、记账、报表），所以 `npm test` 绿着就说明台子能用。
